# 0.1.0 release readiness — what's missing, and the ropes that would break it

> 2026-07-25. Answers the operator's question ("what's missing to release 0.1.0?") and his fear
> ("do a release and watch it break on a rope we never stretched"). Grounded in a full read of the
> release machinery. Companion to `docs/v0.1.0-release-gate.md` and `packages/DISTRIBUTION_STATUS.md`.

## How a release is cut today

- **Policy** lives in `refarm.config.json` under `releasePolicy` (not a standalone file): `mode:
  "changeset"`, three `selections` — `kernel-candidates` (default, 4 pkgs), `kernel-contracts`,
  `vault-seed-ready` (23 pkgs) — over ~40 `packageProfiles`.
- **`packages/release-engine`** is pure planning (`buildReleasePlan`/`runReleaseGates`); `refarm
  release plan|preflight|gates` wraps it. Neither publishes.
- **Two publish lanes:** (1) **changesets** (`release-changesets.yml`) — intentionally **inert**:
  `check-first-publish-changesets.mjs` hard-blocks changeset versioning while any selected package
  is at `0.1.0` (all are). (2) **first-publish** (`scripts/first-publish-selection.mjs` +
  `first-publish-selection.yml`, manual) — the intended 0.1.0 path: resolves `vault-seed-ready`,
  requires `--confirm`, runs `pnpm publish --access public --provenance` per-package topologically.
- **Posture: HELD.** Publication is frozen (declared `v0.0.1-dev`; every package.json stamped `0.1.0`
  awaiting first publish) until Refarm is the creator's daily driver or a human overrides.

## The un-stretched ropes (each would let a release "pass then break")

1. **Build-before-publish is MISSING — the big one.** `dist/` is gitignored and untracked; the
   first-publish workflow does checkout → install → plan → audit → publish-dry-run → publish with
   **no build step**, and no package has a `prepack`/`prepublishOnly`/`prepare` hook. So a fresh CI
   `pnpm publish` packs tarballs whose `files: ["dist"]` match **nothing** — every package ships
   **without its compiled JS/types**; a consumer's `import` resolves to a non-existent
   `dist/index.js`. And **`pnpm publish --dry-run` does not fail on missing dist**, so every gate
   stays green. This is precisely the "dry-run passes, `npm install` breaks" rope. (`heartwood` is
   worse — its output needs `cargo component build` + `jco transpile` for `pkg/`.)
2. **`@refarm.dev/health` has an unpublishable dep.** It requires `@refarm.dev/config` (`workspace:*`),
   but `config` is in **no selection**. On publish, `workspace:*` → `0.1.0`, so `health@0.1.0`
   depends on `config@0.1.0` which is never published → `npm install @refarm.dev/health` **404s**.
   The other 22 `vault-seed-ready` packages are dep-closed; `health→config` is the single leak.
3. **A naive `pnpm -r publish` (105 non-private pkgs) is a minefield:** 4 apps that must not be on
   npm (`apps/dev`, `apps/farmhand`, `apps/me`, `apps/site`), a public→private broken dep
   (`runtime-operator`→private `prompt-contract-v1`), Rust/WASM packages npm can't build (`agent`,
   `heartwood`, the `-ref`/`-plugin` crates), `plugin-manifest` with no build (empty dist), and
   hygiene holes (`toolbox` has `files:(none)`). **Never run a recursive publish.**
4. **The "consumer install" test doesn't install.** `vault-seed-handoff-consumer-install.mjs`
   validates SHA-256/sizes against **fixture tarballs with fake string contents**; it never
   `npm install`s a real packed tarball nor imports the entrypoint. So Ropes #1 and #2 are **not
   exercised end-to-end** — the "proven" evidence is the local handoff pack, a *different path* from
   the npm publish CI job.
5. **LICENSE hygiene:** no package carries its own `LICENSE` in `files`; some lack a `license` field.
   Non-fatal (npm warns) but poor for a first public release. Plus open Gate-1 items: `@refarm.dev`
   npm publish access not yet confirmed in package.json, branch-protection not applied.

## The smallest coherent 0.1.0 (recommended)

**Ship the 4 `kernel-candidate` contracts and nothing else:**
`@refarm.dev/storage-contract-v1`, `sync-contract-v1`, `identity-contract-v1`, `channel-policy-v1`.

They are the only rope-free blocks: **zero runtime dependencies** (Rope #2 cannot bite), ESM-only,
`dist/` from plain `tsc`, README present, pass `npm publish --dry-run`; `channel-policy-v1` carries a
real consumer proof. (Next-safest if widening: `artifact-contract-v1`, `effort-contract-v1` — verify
their dep lists are empty first.) The full 23-package `vault-seed-ready` set is **not naively
shippable** until Ropes #1 and #2 are closed.

## Pre-release checklist (concrete, ordered)

1. **Build before publish.** Add `turbo run build` (scoped to the selection) + the Rust/`jco` build
   for `heartwood` to `first-publish-selection.yml` **before** publish — OR add `prepack` hooks per
   package. Verify with `npm pack --dry-run` that the tarball file list actually contains `dist/`.
2. **Close `health→config`:** add `@refarm.dev/config` to `vault-seed-ready` (and confirm it is
   itself dep-closed) or drop the runtime dep. (Not needed if shipping only the 4 contracts.)
3. **A REAL install-and-import smoke — SHIPPED (2026-07-25).** `scripts/ci/release-install-smoke.mjs`
   (`pnpm run release:install:smoke`) builds each selected package, `npm pack`s a REAL tarball, `npm
   install`s them into a throwaway consumer, and `import()`s each entrypoint — failing loudly if a
   tarball ships no dist (empty import) or a dep can't resolve (install error). This is the gate that
   catches Ropes #1/#2, which `pnpm publish --dry-run` does not. Proven: the 4 kernel contracts pack
   → install → import cleanly (storage 4, sync 3, identity 3, channel-policy 7 exports). **Still to
   do:** wire it into `release-readiness.mjs`'s step list and the `first-publish` workflow, and run it
   over the wider `vault-seed-ready` set (it will surface Rope #2, `health→config`, as a real
   install failure).
4. **LICENSE hygiene:** add a `license` field + include the root `LICENSE` in each selected
   package's `files`.
5. **Shrink blast radius:** never `pnpm -r publish`; keep the scoped first-publish lane; consider
   marking the 4 apps and non-releasable packages a publish-guard so an accidental recursive publish
   can't fire.
6. **Finish Gate 1:** confirm `@refarm.dev` npm scope publish access; apply branch protection.
7. **Run in order:** `refarm release preflight --selection kernel-candidates --json` →
   `pnpm run release:readiness` → `pnpm run release:boundary:audit` → `first-publish-selection.yml`
   with `dry_run=true`, **inspect the packed file lists**, only then `dry_run=false`.

## Security audit (issues #54/#55) — identified 2026-07-25

**RESOLVED 2026-07-25 (commit `5b522332`, pushed to `develop`).** The Release Health workflow's
"Security audit (high): failure" was **real**: a `pnpm audit --prod` against the public registry
found **11 vulnerabilities (1 critical, 6 high, 3 moderate, 1 low)** — all TRANSITIVE build/app
dependencies, none in a publishable contract. **The 6 high are now fixed** (see "Applied fix"
below); `pnpm audit --prod --audit-level high` exits 0. What remains is deferred/accepted: the 4
astro moderate/low (in HELD apps — the patch breaks the build) and the 1 pre-ignored decompress
critical. The original breakdown:

| Package | Severity | Patched | Where |
|---|---|---|---|
| `astro` | moderate ×3, low ×1 | `7.1.x` (see note) | `apps/{me,dev,site}` (apps are HELD, not published) |
| `postcss` | high | `>=8.5.18` | build tooling (transitive) |
| `sharp` | high | `>=0.35.0` | image pipeline (transitive) |
| `fast-uri` | high ×2 | `>=3.1.4` | transitive |
| `svgo` | high | `>=4.0.2` | transitive |
| `js-yaml` | high | `>=4.3.0` | transitive |

**Key fact for the release:** the smallest-safe 0.1.0 — the 4 zero-dep kernel contracts — is
**CLEAN** (no deps, no advisories). These vulns do not block shipping the 4 contracts; they affect the
apps + build tooling.

**Two environment gotchas found:**
- On the operator's **corporate network (Serpro)**, `pnpm audit`/`--fix` hit the corporate **Nexus
  proxy, which returns HTTP 400** for the advisory endpoint — so the audit can't run there. Use
  `pnpm audit --prod --registry=https://registry.npmjs.org/` (read works), or run on a non-corporate
  network / CI (CI has direct npm access, which is why the CI audit *does* find them).
- **`security:fix` masked the failure — FIXED (commit `e5d9580b`).** On the 400 it used to print
  "✅ No vulnerabilities — nothing to fix" (why issue #55's body said "no vulnerabilities" while #54
  said "high: failure"): it did `JSON.parse(stdout || "{}")` and never checked the exit code or a
  spawn error, so empty/error-page output parsed to `{}` → zero vulns → a dangerous false-clean.
  `parseAuditReport()` (pure, in `audit-fix-lib.mjs`) now returns `{ok:false}` for a spawn error or
  empty/unparseable stdout, and the orchestrator exits 2 with the reason instead of reporting clean.
  Six regression tests in `scripts/ci/test-security-audit-fix-lib.mjs` (`pnpm run security:fix:test`).

**Applied fix (2026-07-25, commit `5b522332`).** In `pnpm-workspace.yaml` `overrides:`:
- `js-yaml`: raised the blanket pin `4.2.0 → 4.3.0` (4.2.0 was itself `<4.3.0` vulnerable — a
  blanket, so it beat any conditional; had to edit the pin itself).
- Added conditional bumps (only the vulnerable ranges): `fast-uri@>=3.0.0 <=3.1.3 → ^3.1.4`,
  `postcss@<=8.5.17 → ^8.5.18`, `sharp@<0.35.0 → ^0.35.0`, `svgo@>=4.0.0 <4.0.2 → ^4.0.2`.
- **`brace-expansion`** across four major lines (`<1.1.16 → ^1.1.16`, `>=2.0.0 <2.1.2 → ^2.1.2`,
  `>=3.0.0 <5.0.7 → ^5.0.7`, `<=5.0.7 → ^5.0.8`) — a **dev-dep** DoS high (commit `b26b7f91`). Two
  audit SCOPES exist in CI and this hid between them: Release Health + Security Audit run `pnpm audit
  --prod` (prod deps, never saw it); **Test & Quality runs `pnpm audit --audit-level=high` WITHOUT
  `--prod`** (dev deps too) and failed on it. Fixing one gate is not fixing "the audit" — check both.
- **`astro` deliberately NOT bumped.** Its advisory says "patched `>=7.0.10`", but `7.0.10` does
  not exist — the line goes `7.0.9 → 7.1.0` (latest `7.1.3`), so the fix is a `7.0 → 7.1` MINOR bump.
  **Verified that bump breaks the apps:** on astro `7.1.3` the Rolldown-Vite bundler rejects a
  cross-package re-export (`Missing export buildJsonSuccessEnvelope from
  @refarm.dev/capabilities/envelope`); the apps build cleanly on `7.0.3` and fail on `7.1.3`. The 4
  astro advisories are moderate/low and live only in the HELD apps, below the "high" gate. Fixing
  them = migrating the apps to astro 7.1 (its own task — a real code-compat change, not an override).
- `dompurify` was left at `3.4.11`; the current audit does not flag it.

**Verification (this machine, public registry):** BOTH audit scopes exit 0 — `pnpm audit --prod
--audit-level high` AND `pnpm audit --audit-level high` (non-prod, dev deps); all apps build
(`turbo run build --filter='./apps/*'` → 78/78); reqbench-t3 tests pass; astro unchanged at 7.0.3.
The environment gotchas above are resolved: the Nexus 400 by the committed `.npmrc`
`registry=https://registry.npmjs.org/` override (commit `0a0a5aa7`, global corporate config
untouched), and the `security:fix` false-clean masking by `parseAuditReport()` (commit `e5d9580b`).

## Bottom line

The machinery is real and mostly present; the gap is not tooling but **an un-stretched integration
path**: nothing today packs a built tarball and installs+imports it. Fix #3 (the real install smoke)
and #1 (build-before-publish), ship the 4 contracts first, and the release stops being a leap of
faith. The 23-package set follows once its two ropes are closed.
