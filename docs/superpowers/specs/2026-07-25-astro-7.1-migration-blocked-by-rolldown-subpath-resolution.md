# astro 7.1 migration — blocked by Rolldown-Vite subpath-export resolution

> 2026-07-25. Root-cause investigation for issue #56 ("Security Audit: Moderate Vulnerabilities").
> The astro advisories (3 moderate + 1 low) are patched only in astro `>=7.0.10` = `7.1.x`. Bumping
> the apps to astro 7.1 is a real code migration, not a version pin — this documents why, so the
> work survives for a dedicated effort. Companion to `docs/2026-07-25-v0.1.0-release-readiness.md`.

## The goal and the blocker

Clear the 4 astro advisories (issue #56) by moving the apps (`apps/{me,dev,site}`, +`homestead`,
`ds-astro`) from astro `7.0.3` to `7.1.x`. **The apps build cleanly on `7.0.3` and fail on `7.1.3`.**

Root cause (verified, not guessed): **astro 7.1's bundler is Rolldown-Vite (rolldown `1.0.3`), and it
mis-resolves a workspace package's SUBPATH export to the package's `.d.ts` file instead of its `.js`.**
A `.d.ts` is `export declare function …` — declarations, zero runtime value — so the transformed
module has no exports and rolldown fails:

```
[MISSING_EXPORT] "buildJsonErrorEnvelope" is not exported by ".../packages/capabilities/dist/envelope.d.ts"
  imported by packages/capabilities-v1/dist/records-capability.js:
  import { buildJsonErrorEnvelope, buildJsonSuccessEnvelope } from "@refarm.dev/capabilities/envelope";
```

## Evidence gathered (systematic-debugging Phase 1–3)

1. **Reproducible & version-bound:** `turbo build --filter='./apps/*'` → 78/78 on astro `7.0.3`;
   the same build fails on `7.1.3`. Nothing else changed.
2. **The `exports` map IS honored — it is not staleness or a missing file.** `dist/envelope.js`
   exists and exports `buildJsonSuccessEnvelope` directly. Pointing the export at a *different* file
   proves the map is read: `"./envelope": { "import": "./dist/index.js" }` makes rolldown load
   `dist/index.js` (error moves to "not exported by dist/index.js"). So rolldown follows the map.
3. **The bug is SUBPATH-specific.** The MAIN export (`.`) resolves to `.js` correctly; only SUBPATH
   exports (`./envelope`) resolve to `.d.ts`. `dist/index.js` (main) → `index.js`; `dist/envelope.js`
   (subpath) → `envelope.d.ts`. Same directory, same co-located `.d.ts`, opposite outcome.
4. **Condition order and the `types` condition are NOT the cause.** Reordering to `import`-first
   (matching the working `capabilities-v1`) did not help; removing the `types` condition entirely did
   not help. rolldown still loads the `.d.ts`.
5. **It is SYSTEMIC, not one package.** Aliasing `@refarm.dev/capabilities/envelope` to source (the
   repo's existing `coreAstroAliases` escape-hatch) fixed that import — and the build then failed on
   the next one, `@refarm.dev/cli/chat-repl` (`parseChatLine not exported by …/cli/dist/chat-repl.d.ts`).
   The apps consume **dozens** of `@refarm.dev/*/subpath` exports (`@refarm.dev/cli/*` alone is ~25:
   chat-repl, chat-history, command-handoff, execution-plan, launch-policy, …), plus
   `capability-host/testing`, `ds/components`, `ds/html`, `agent/package`, and more.

## Why per-subpath aliases are the wrong fix

`coreAstroAliases` in `packages/config/src/astro.js` already aliases a few subpaths (tractor, config)
to source. Extending it to every affected subpath would mean ~30+ fragile alias entries that must be
kept in lockstep with every new subpath export — whack-a-mole over a bundler bug, and a net *loss* of
"best state" (brittle config hiding a systemic issue). Rejected.

## Decision

**Stay on astro `7.0.3`.** The apps are HELD (never published), and the 4 advisories are moderate/low
and below the "high" audit gate — the smallest-safe 0.1.0 (the 4 zero-dep contracts) is unaffected.
Forcing 7.1.3 with band-aids makes the project worse, not better. Issue #56 stays deferred, now with a
real root cause instead of a guess.

## Paths forward (for the dedicated effort)

Ordered by preference:

1. **Wait for / track an upstream fix.** `7.1.3` is the latest astro as of this writing and bundles
   rolldown `1.0.3`. This is a rolldown resolver bug (subpath export → `.d.ts`). Re-test on each astro
   7.1.x / rolldown bump; the migration may become a no-op version bump once fixed. **Lowest cost —
   check first.**
2. **A single central resolution fix**, if one exists: a vite `resolve` plugin (or option) that forces
   `@refarm.dev/*/*` subpath specifiers to their `.js` target, applied once in `coreAstroAliases`'s
   host (`packages/config/src/astro.js`) so all apps inherit it. Must be driven by a rule, not an
   enumerated list. Investigate whether rolldown exposes a knob to exclude `.d.ts` from module
   resolution, or whether a `resolveId` hook returning the `.js` for any resolved `.d.ts` works.
3. **Restructure the packages' `exports`** so the subpath cannot resolve to a `.d.ts` — e.g. ship the
   subpath's types via `typesVersions`/co-location without a `types` condition, or split the runtime
   entry so rolldown resolves `.js`. NOTE: evidence #2/#4 show the map is honored and the `types`
   condition is not the trigger, so this may not help — validate against a minimal repro before
   committing to a repo-wide `exports` change.

**A minimal reproduction** (one package, one subpath, astro 7.1.3) belongs in any upstream issue and
should be the first artifact of the dedicated effort — it isolates the bug from this monorepo's size.

## What was NOT changed

All experiments were reverted; the tree is back to the working astro `7.0.3` state. The security work
that closed #54/#55 (the 10 high advisories) is independent and remains committed.
